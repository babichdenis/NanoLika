## Найденные проблемы и исправления

### 1. Высокий приоритет: HTTP сохраняет старое окружение после выгрузки

`cloud_worker.py`, строки 45 и 48: отдельный словарь apps хранит приложение с привязанным сервисом. `AccountRuntime.stop()` удаляет сервис из своего реестра, но не удаляет приложение из apps. После повторного создания сервиса sub_app() возвращает старое приложение. HTTP может работать с остановленным сервисом, тогда как WebSocket получает новый.

Проверка: извлечённая из исходника функция sub_app() с подставленным конструктором возвращает первый сервис после передачи нового сервиса для того же аккаунта. Результат: `old service reused by HTTP after replacement: True`.

Исправление: связать кэш приложения с конкретным экземпляром сервиса или хранить приложение и сервис в одной записи реестра; инвалидировать их вместе. Приёмка: HTTP и WS после TTL, вытеснения и повторного входа работают с одним новым сервисом; старый освобождён.

### 2. Высокий приоритет: обновлённый ключ игнорируется для активного окружения

`web_runtime.py` выдаёт ключ примерно на шесть часов и обновляет его. В `accounts.py:90` уже существующая запись возвращается до обработки нового cloud_key. Сохранение ключа в vault происходит только при _build(). Постоянно активный аккаунт может продолжить работу с истёкшим ключом.

Проверка: два вызова service() для одного аккаунта с разными ключами, конструктор получил только первый ключ. Само истечение ключа и запрос к провайдеру не воспроизводились.

Исправление: обновлять ключ активного окружения и использующих его клиентов при ротации. Приёмка: запрос после ротации использует новый ключ без потери истории и текущих заданий; старый ключ больше не применяется.

### 3. Высокий приоритет: выгрузка не учитывает выполняемую работу

`accounts.py:126` выбирает старейшее окружение без проверки активного задания или WS. sweep() проверяет время последнего получения сервиса. Сообщения длительного WS не обновляют used. `MuseService.stop()` отменяет работающие задачи и планировщик.

Следствие по коду: открытый чат или длительная задача могут быть остановлены при TTL или вытеснении. Это не подтверждение потери конкретного пользовательского задания на сервере.

Исправление: учитывать активные запросы, соединения и задания; не выгружать занятые окружения. Отделить устойчивые фоновые задания и напоминания от времени жизни загруженного сервиса. Приёмка: долгая задача и WS переживают TTL; напоминание срабатывает при выгруженном аккаунте; перезапуск не вызывает потери задания или двойного списания.

### 4. Средний приоритет: лимит окружений нарушается при параллельном создании

Замок в service() отдельный для каждого аккаунта. Между _make_room() и записью результата _build() другой аккаунт может тоже пройти проверку ёмкости.

Проверка: два параллельных создания с лимитом 1 дали два активных окружения. Использован настоящий код реестра с подставленным асинхронным конструктором сервиса.

Исправление: общий контроль резервирования ёмкости с учётом создаваемых окружений, согласованный со stop/sweep. Приёмка: при параллельной нагрузке число занятых мест не превышает лимит; занятые окружения не отменяются ради освобождения места.

### 5. Требует подтверждения: доверие внутренним заголовкам

Работник принимает X-Account и X-Cloud-Key и сам добавляет токен доступа к API сервиса. Отдельной проверки подлинности релея в проверенных обработчиках работника нет. По умолчанию он слушает loopback, но реальное сетевое ограничение контейнерного развёртывания этой проверкой не подтверждено.

Исправление: подтвердить недоступность работника из внешней сети и ненадёжных контейнеров; добавить проверяемую служебную аутентификацию релея. Заголовки браузера по текущему коду релей отбрасывает, поэтому это не установленный обход входа через публичный прокси.

## Как проверялось

Прочитаны исходники прокси, реестра, работника, генератора документов и остановки MuseService. Для трёх случаев выполнены небольшие воспроизводящие проверки извлечённых из исходников функций с подставленными сервисами: ротация ключа, параллельный лимит и кэш приложения. Они проверяют указанную логику, а не полный запуск окружения.

Полноценный прогон через Python-окружение не завершился в пределах проверки; его результат не засчитывается. Полный набор тестов, платные запросы, рабочий сервер и клиентские сборки не проверялись. Исходники не изменялись, установщики не пересобирались.

## Очерёдность завершения

1. Исправить кэш HTTP и ротацию ключей.
2. Защитить занятые окружения от выгрузки и согласовать лимит параллельного создания.
3. Проверить доверие к работнику и изоляцию файлов и секретов.
4. Довести устойчивые задания и планировщик для выгруженных аккаунтов.
5. Выполнить сквозную приёмку двух обычных аккаунтов с проверкой оплаты, перезапуска, длительного WS и TTL.
6. Проверить нагрузку и откат, затем расширять допуск за пределы пилота.
