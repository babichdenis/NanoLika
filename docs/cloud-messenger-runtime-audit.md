# Telegram и MAX: облачные файлы без компьютера

Проверка 2026-11-11. Это отчёт о текущем состоянии и незавершённых работах; он не означает, что новый механизм включён.

## Обновление 2026-11-11

- Синхронизация больше не должна присваивать аккаунту установки беседы с областью другого клиента, а файлы из несовпадающего пространства не загружаются в хранилище владельца установки. Устаревшие личные беседы без владельца по-прежнему допускаются к переносу; для старых тем мессенджеров принадлежность должна быть подтверждена.
- При проверке изолированного снимка действующего `nanomuse/sync/engine.py` тест `test_a_chat_keeps_its_own_model_everywhere` иногда не дождался применения выбранной на другом устройстве модели. То же падение воспроизведено на исходном снимке до защиты владельца чата. Диагностика выявила вероятную причину в тестовом релеe: при стартовой загрузке он может передать номер последнего изменения, не передав при этом саму основную беседу без сообщений. Реализация настоящего релея по коду добавляет основную беседу в такой ответ. Проверка использовала локальный тестовый релей и остальные локальные компоненты; это не подтверждает работу или неисправность на настоящих устройствах.
- Ошибки получения вложений в Telegram и MAX больше не запускают запрос с неполным набором файлов. Передача вложений через `/computer` пока не реализована: бот честно сообщает об этом.
- Для файлов, созданных ботом, ссылки больше не должны использовать ключ постороннего аккаунта; отсутствие файла в папке клиента не вызывает поиск одноимённого файла в общей папке оператора. Проверены два канала, разные состояния ключа и сквозной тест приёма, изменения и возврата файла с тестовым каналом. Реальную доставку через приложения Telegram и MAX после установки ещё нужно проверить.
- Для новых ответов лёгкого веб-чата сохраняются токены и стоимость с привязкой к сообщению и аккаунту. Старые ответы автоматически связать со списаниями нельзя. Для отдельных ответов Telegram, MAX и десктопа эта связь ещё не реализована; использовать разницу общего баланса нельзя, потому что параллельные чаты могут смешаться.
- Исправлено списание при потоковом ответе с ключом клиента: расходы остаются у его поставщика и не списываются второй раз с баланса nanoLika. Данные прошлых списаний этим исправлением не пересчитываются.
- Исправлен показ нового API-ключа, если создание прошло успешно, но обновление списка ключей не удалось. До копирования ключ остаётся видимым.

Эти исправления не закрывают описанный ниже переход к безопасной полноценной облачной работе с файлами и кодом. Компьютер по-прежнему нужен для запросов, которым необходимы его локальные данные или программы.

## Что работает сейчас

- При обычном сообщении Telegram или MAX `ChannelManager` сохраняет принятые вложения и запускает `MuseService` в процессе бота. `cloud_per_chat` выбирает ключ и модель аккаунта для оплаты запроса, но не переключает запуск в `cloud-worker`.
- `/computer` передаёт текст на компьютер отдельно. Это не решение для работы без включённого компьютера.
- У `cloud-worker` есть `AccountRuntime`, отдельные папки и `MuseService` для каждого аккаунта, однако все сервисы находятся в одном процессе. В этой конфигурации `shell`, `python_execute` и `coding_agents` по умолчанию намеренно отключены: без изолированного окружения произвольный код мог бы прочитать данные других пользователей.
- У worker существуют HTTP-интерфейсы загрузки файлов (`POST /api/files/upload`), отправки сообщения (`POST /api/threads/{id}/send`), чтения событий (`GET /api/threads/{id}/events`) и скачивания (`GET /api/files/{path}`). Релей принимает Bearer-ключ, проверяет аккаунт и сам добавляет доверенные заголовки для worker. Существование этих интерфейсов само по себе не обеспечивает сквозную работу Telegram/MAX.
- В работающем контейнере бота доступны библиотеки для DOCX и XLSX. В отдельной временной папке файлы этих форматов создавались, редактировались и открывались повторно. Это проверка библиотек, а не проверка сквозной доставки в мессенджер.

## Что необходимо сделать до включения

1. **Граница исполнения.** Создать действительно изолированное окружение для задач каждого аккаунта: отдельный непривилегированный контейнер или другой проверенный механизм ограничения доступа к файлам, процессам, сети и ресурсам. Разрешать выполнение кода только внутри этой границы. Проверить попытки чтения чужого аккаунта, служебных ключей и файлов хоста. Включать произвольный код в текущем общем процессе нельзя.
2. **Доверенная идентификация и беседа.** Получать аккаунт только из проверенной сервером привязки мессенджера. Сопоставлять общий идентификатор облачной беседы с конкретной беседой в runtime; перед началом задания подтягивать её историю и не смешивать темы. Не принимать идентификатор владельца из текста или произвольного клиентского поля.
3. **Приём вложений.** Передавать все полученные файлы в workspace выбранной беседы через проверенный API; при любой ошибке показывать, какие файлы не получены, и не запускать запрос с неполным набором. Нужен механизм удаления уже загруженных частей при ошибке и ограничение размера без загрузки произвольного объёма в память. Существующий публичный API удаления загруженного файла в просмотренном пути не найден.
4. **Повтор и восстановление.** Добавить сохраняемый на стороне worker ключ операции на основе доверенного источника и ID сообщения, атомарно связанный с созданием пользовательского события и постановкой задачи. Повтор после сетевого обрыва должен возвращать то же задание, а не запускать ещё один платный запрос. Одной локальной квитанции недостаточно: ответ может потеряться после принятия задания и до записи квитанции.
5. **События и результат.** Привязать поток событий и артефактов к конкретному заданию, дождаться завершения, а не считать любой текст из истории ответом. Скачивать готовые файлы только из пространства этого аккаунта и этой беседы и отправлять их в исходный Telegram topic или чат MAX. Сохранять состояние доставки и безопасно повторять её после перезапуска, не рассылая дубли.
6. **Работа без компьютера.** Для облачной задачи не выбирать компьютер автоматически. Если запрос требует файлов, программ или состояния домашнего компьютера, при его отсутствии прямо сообщать об этом; после включения устройства синхронизировать общую беседу, не выдавая чужие локальные файлы за облачные.
7. **Проверки перед запуском.** Автоматические тесты двух аккаунтов и двух бесед; повторов и параллельных сообщений; обрыва после принятия и при загрузке нескольких вложений; недоступного worker; перезапуска; ограничений формата и размера; отсутствия доступа к чужим файлам. Отдельные сквозные проверки реальных Telegram и MAX: получить DOCX/XLSX, внести изменение, вернуть проверенный файл в исходную тему, продолжить диалог при выключенном компьютере и открыть историю после включения. Указывать поддерживаемые форматы по фактическим проверкам, а не обещать обработку произвольного файла.

До выполнения этих пунктов переключать действующего бота на новый путь рано. Временный прототип клиента, который не обеспечивал восстановление, привязку результатов и доставку, удалён; в рабочем дереве не оставлен.

## Проверка изолированной обработки DOCX/XLSX на сервере

11 ноября 2026 года проведён одноразовый тест с искусственными данными в отдельном Docker-контейнере из существующего образа `nanomuse:worker-20261110`. Контейнер запущен без сети и сокета Docker, под UID 1000, с корневой файловой системой только для чтения, без capabilities, с `no-new-privileges`, seccomp и лимитами 256 МиБ, 64 процесса и 1 CPU. Для записи была доступна только специально созданная тестовая папка; `/tmp` был отдельным tmpfs. Проверка подтвердила, что контейнер не видит тестовый маркер снаружи папки, а также что DOCX и XLSX удаётся создать, изменить и повторно прочитать. Тестовый контейнер и папка удалены. Действующие сервисы и клиентские файлы не менялись.

На сервере доступны Docker 29.1.3, cgroup v2, AppArmor и стандартный seccomp. У бота и worker процессы запущены под UID 1000; bwrap в их контейнерах не найден. Бот уже работает с `read-only` root и лимитами; общий worker не имеет отдельных контейнерных лимитов памяти или процессов. В обоих есть библиотеки `python-docx` и `openpyxl`. Общий процесс worker по-прежнему не является границей между аккаунтами.

Практический путь: отдельный краткоживущий контейнер на задачу, запущенный доверенным контроллером без передачи ему ключей и доступа к Docker из самого контейнера; ограниченные входная папка только для чтения и выходная папка для записи, без сети, со всеми перечисленными ограничениями и таймаутом. Для реальной эксплуатации нужен отдельный проверенный минимальный образ: существующий worker-образ применён только для проверки, что библиотеки и ограничения совместимы. Контроллер обязан привязывать каждую задачу и её файлы к проверенному аккаунту и беседе, проверять выходные файлы и не следовать ссылкам за пределы рабочей папки; ограничивать размер и время обработки повреждённых или слишком больших архивов, убирать временные файлы и контейнеры при сбоях. Результат затем должен передаваться через проверенный мост событий и вложений. Раздельные тесты нескольких клиентов, проверка конфигурации образа, контроллера и границ доступа обязательны до подключения пользователей. Успешный пробный запуск не доказывает безопасность от всех способов выхода из контейнера и не подтверждает работу через настоящие Telegram/MAX.

## Контракт будущего изолированного обработчика

Это проект контракта, а не работающий API. Текущие `/v1/files/{key}` открывают файл по подписанной ссылке без проверки аккаунта предъявителя; такую ссылку нельзя использовать как подтверждение личности владельца результата. Кроме того, `caller_dep` специально ограничивает пользовательские API-ключи модельными методами. Для заданий нужен отдельный узкий служебный доступ через релей; расширять права пользовательских ключей на произвольные серверные операции нельзя.

1. Релей проверяет подлинность входа и права на беседу существующими механизмами. Затем выдаёт короткоживущее служебное утверждение строго для контроллера заданий с `account_id`, идентификатором беседы и сообщения, назначением, сроком и одноразовым идентификатором. Идентификаторы из текста сообщения, имена локальных файлов и произвольный заголовок клиента владельца не определяют. Контроллер проверяет подпись, назначение и срок; секрет подписи недоступен боту, модели и контейнеру.
2. `POST /internal/document-jobs` принимает служебное утверждение, ключ операции, ограниченную спецификацию задачи и непрозрачные идентификаторы входных объектов. Релей или контроллер заново проверяет принадлежность каждого объекта аккаунту и беседе. Повтор того же ключа с теми же данными возвращает существующее задание; другие данные с тем же ключом отклоняются. Размеры входа, распаковки, число файлов и одновременных заданий ограничены для каждого аккаунта.
3. Перед запуском фиксируются состояние задания и его детерминированный идентификатор контейнера. Доверенный контроллер самостоятельно создаёт изолированный контейнер; ни бот, ни worker, ни сам контейнер не получают Docker socket. Не допускаются пользовательские образы, параметры Docker, переменные окружения, bind mounts и путь на хосте. Контейнер получает только подготовленные ему файлы, сеть выключена, root read-only, непривилегированный UID, seccomp/AppArmor, `cap-drop=ALL`, `no-new-privileges`, лимиты памяти, CPU, процессов, времени и места. Выход размещается в ограниченном по размеру tmpfs, а не в неограниченной общей папке. Контейнер также должен быть изолирован от учётных данных и внутренней сети сервиса.
4. `GET /internal/document-jobs/{job_id}` возвращает состояние только доверенному вызывающему компоненту после сверки аккаунта и беседы. Результаты забираются через отдельный авторизованный поток и выдаются клиенту только после той же проверки. При извлечении архивов и файлов запрещены абсолютные пути, переходы `..`, символьные и жёсткие ссылки, устройства и выход за выделенную папку; ограничиваются размер и количество объектов. Ошибка или отсутствие файла не превращаются в сообщение об успешном результате.
5. Состояния как минимум: принято, подготовка, выполняется, результат сохранён, ошибка, отменено, исход неизвестен. После перезапуска контроллер сверяет зарегистрированное задание и контейнер; при неизвестном результате не запускает код повторно вслепую. Очиститель удаляет завершённые и зависшие контейнеры и временные данные с учётом срока хранения. Подтверждение доставки в конкретную тему Telegram/MAX хранится отдельно от завершения выполнения и позволяет безопасно повторять её после сбоя.
6. До включения нужны сквозные проверки двух аккаунтов и тем, подмены идентификаторов и входных файлов, повтора и гонок, отмены и таймаута, перезапуска на каждом переходе, недоступности Docker/хранилища/мессенджера, переполнения места и памяти, опасных имён и ссылок, а также настоящего DOCX/XLSX в обоих мессенджерах при выключенном компьютере. Логи не должны содержать ключи, код задания или содержимое документов.

Реализация этого контракта требует согласованных изменений релея, доверенного контроллера, хранения файлов и интеграции бота. Тест отдельного контейнера выше не предоставляет этих гарантий; неполный сервер с доступом к Docker в действующие компоненты не внедрён.
