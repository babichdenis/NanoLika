# Облачный рантайм на аккаунт: план на 2–4 недели

**Статус:** план. Ничего из этого ещё не включено.
**Зачем документ:** объяснить, почему Word/Excel/презентации/картинки/видео/архивы
у владельца работают, а у посетителя в вебе — нет, и что именно надо построить,
чтобы работало у каждого. Оценки — из аудитов `NanoLika-onboarding` (§4 п.8:
3–4 недели) и `NanoLika-cloud-worker-cheaper` (§4: реестр, а не процесс на
аккаунт).

## 1. Что уже есть у владельца

Всё это живёт в одном процессе `nanolika-bot` (`nanolika-bot:8799`), у него есть
файловая система контейнера, Python-библиотеки и ключи:

| Умение | Чем сделано | Где живёт |
| --- | --- | --- |
| Word | навык `office-docx` + `python-docx` | рантайм, файл в workspace |
| Excel | `office-xlsx` + `openpyxl` | там же |
| Презентации | `office-pptx` + `python-pptx` | там же |
| Картинки | инструмент `picture` → релей `/v1/images/*` | рантайм + релей |
| Видео | инструмент `video` → релей | рантайм + релей |
| Архивы | `zipfile` в Python-песочнице | рантайм |
| Файлы, папки, экран, команды | `files`, `shell`, `python_execute`, `computer`, `phone` | рантайм |
| Память, цели, напоминания | SQLite + фоновые петли `MuseService` | рантайм |

Посетитель в вебе получает только `deepseek-flash` и текст: у лёгкого клиента
(`/web/`) нет ни инструментов, ни файловой системы, ни процессов. Поэтому
«сделай Excel» у него превращается в совет поставить приложение.

## 2. Почему нельзя просто «открыть» этот рантайм всем

1. **Один процесс — один аккаунт.** `MuseService` держит один `workspace`
   (`server/service.py`), одну базу памяти (`memory/store.py`), один Sentinel.
   Если пустить туда второго человека, он увидит файлы, память и цели первого.
   Аудит `NanoLika-isolation-razbor` (I1–I3) показывает это прогонами.
2. **Инструменты — это процесс, а не HTTP.** `python-docx`, `openpyxl`,
   `python-pptx`, `zipfile`, `ffmpeg` и браузер требуют файловой системы и
   дочерних процессов. Релей — FastAPI, он не должен исполнять чужой код в своём
   процессе. Браузеру и офису нужен отдельный воркер.
3. **Ключи и модели.** У каждого аккаунта свой Cloud-ключ, свой остаток и своя
   модель. Общий процесс тратит ключ владельца на чужой запрос.
4. **Фоновые петли.** Напоминания и цели срабатывают в свою минуту; значит,
   кто-то должен быть жив, даже когда человек спит. Один общий бот этого не
   делает для чужих аккаунтов.
5. **Файлы и ссылки.** Документ надо положить в S3 аккаунта и отдать ссылку,
   которую увидят все его устройства и мессенджеры. Это делает воркер с его
   ключом, а не общий релей.

## 3. Целевая схема

```
Telegram/MAX ─┐
Веб /web/ ────┼─► релей: аккаунт, деньги, модели, сессия
              │        │
              │        ▼
              │   планировщик (один): напоминания, цели, тики — по минуте
              │        │
              │        ▼
              └─► пул воркеров (8 штук): MuseService на аккаунт
                       │  data_dir=/data/accounts/<id>
                       │  workspace=/data/accounts/<id>/workspace
                       │  память/цели — в том же томе
                       ▼
                  S3 аккаунта + модель аккаунта
```

Не «процесс на аккаунт»: по замерам пустой аккаунт внутри процесса — **4 МБ и
30 мс**, процесс — 107 МБ. Восемь воркеров держат сотни аккаунтов, потому что
люди не пишут одновременно. Простаивающий аккаунт гасится, состояние остаётся
на диске.

## 4. План по неделям

### Неделя 1. Реестр аккаунтов и маршрутизация (ядро)

**Цель:** два аккаунта (владелец и тестовый) одновременно получают в вебе
Word/Excel/архив и не видят друг друга.

- `AccountRuntime`: настройки на аккаунт (`data_dir`, Cloud-ключ, модель,
  `customer_scope`), создание/поиск `MuseService`, TTL простоя.
- Реестр в процессе воркера: `account_id → MuseService`, предел (например, 50),
  вытеснение самого давнего, отдельный `data_dir` на аккаунт.
- Релей: `/api/*` и `/ws` маршрутизируются по аккаунту из сессии; страница
  `/web/` отдаёт клиент рантайма **своего** аккаунта, лёгкий клиент остаётся для
  mini app и гостей.
- Вход: сессия релея → ключ аккаунта для воркера; в браузер ключ воркера не
  попадает.
- Инструменты недели: `office-docx`, `office-xlsx`, `zip`, `files` (чтение и
  запись внутри workspace аккаунта).

**Проверка:** два браузера, два аккаунта: документ одного не открывается у
другого; `/api/threads` возвращает только свои беседы; файл из S3 доступен
только по своей ссылке.

### Неделя 2. Изоляция данных, файлы, лимиты

**Цель:** аккаунт не может прочитать чужое даже при ошибке в инструменте.

- `workspace` на аккаунт, а внутри — папка на тред (`workspace_for(thread)`);
  `save_upload` кладёт вложение в папку треда.
- Память: колонка `scope`, `relevant()` фильтрует по разрешённым областям;
  общая память аккаунта — только то, что человек сам добавил.
- Sentinel: `full-access` не снимает taint; границы путей — корень аккаунта.
- Квоты: диск на аккаунт, число тредов, размер вложений, TTL файлов
  (`keep_files_hours` на аккаунт, а не один на всех).
- S3: воркер кладёт результат своим ключом, ссылка — `media_url` аккаунта.

**Проверка:** сценарии I1–I3 из `NanoLika-isolation-razbor` зелёные на двух
аккаунтах; чужой файл и чужой факт не появляются в промпте.

### Неделя 3. Пул, планировщик, медиа

**Цель:** воркеры не висят вечно; напоминания срабатывают без компа; картинки,
видео и презентации доходят файлом.

- Пул из N воркеров + очередь: релей кладёт ход, воркер берёт, поднимает
  состояние аккаунта (30 мс), отвечает, отдаёт.
- Планировщик: раз в минуту смотрит напоминания/цели/триггеры всех аккаунтов и
  будит нужный воркер. Он же — единственное место, где живут часы.
- TTL простоя: аккаунт без запросов N минут освобождает воркер; состояние
  остаётся на диске, следующий ход поднимает его.
- Медиа: `picture`, `video`, `office-pptx` → файл → S3 → сообщение в веб и
  мессенджер; архивы (`zip`) собираются из файлов аккаунта.
- Нагрузка: замер RSS на аккаунт с сотней тредов, p95 хода, холодный старт.

**Проверка:** 10 аккаунтов, 8 воркеров, одновременные запросы; напоминание
срабатывает при закрытом браузере; видео и презентация приходят файлом в веб и
в Telegram.

### Неделя 4. Пилот и запуск

**Цель:** пустить людей и не потерять данные при сбое.

- Пилот на 5–10 реальных аккаунтах; регистрация, вход, документы, файлы,
  напоминания.
- Тесты изоляции и «чужой не видит» на живом; журнал ошибок, метрики по
  аккаунтам, алерты.
- Откат: аккаунт можно вернуть на лёгкий клиент; данные не теряются.
- Документация: «что умеет веб», «что умеет приложение», «где лежат файлы».
- Только после этого — открывать регистрацию шире.

## 5. Что делаем параллельно, не дожидаясь рантайма

Простейшие документы уже можно давать всем без воркера — и это не отменяется:

- Word — сделано (`/v1/documents`, инструмент `make_document`).
- Excel, презентации, архивы — тем же путём на релее (генерация файла и ссылка),
  если не нужны правки и чтение чужих файлов.
- Картинки — уже есть на релее (`/v1/images/*`); нужен только инструмент в
  лёгком клиенте.
- Видео — релей умеет, нужен инструмент и доставка файла.

Это закрывает «простейшие документы» у всех на этой неделе, пока строится
рантайм. Рантайм нужен для того, что требует файловой системы и нескольких
шагов: прочитать присланный файл, поправить его, собрать архив, сделать
презентацию из таблицы, сохранить и переслать.

## 6. Чего не делаем

- **Не process-per-account.** 107 МБ × N не масштабируется; пул дешевле.
- **Не пускаем чужих в общий `nanolika-bot`.** Это чужие файлы, память и ключ.
- **Не даём браузеру ключ воркера.** Только сессия релея и прокси.
- **Не смешиваем аккаунты без `customer_scope`.** Память, цели, файлы — свои.
- **Не обещаем «полный компьютер».** Руки (экран, программы) — отдельное
  согласие и отдельные права; в плане их нет.

## 7. Критерии приёмки

1. Два аккаунта в двух браузерах: Word/Excel/архив делаются, файлы не видны
   друг другу.
2. Посетитель без почты: вход, документ, ссылка, баланс — без установки
   приложения.
3. Напоминание срабатывает при закрытом браузере и выключенном компьютере.
4. 10 одновременных аккаунтов не роняют воркеры; p95 хода не хуже, чем у
   владельца сейчас.
5. Откат аккаунта на лёгкий клиент не теряет ни одного сообщения.
