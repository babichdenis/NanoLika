## Как устроено меню

После запуска бот отправляет приветствие с постоянной клавиатурой:

| Первый столбец | Второй столбец |
| --- | --- |
| Чаты | Новая беседа |
| Модели | Баланс |
| Настройки | Помощь |

Отдельная нативная кнопка «Открыть Лику» ведёт в `https://cloud.nanolika.ru/web/telegram.html` с проверкой Telegram-входа.

Прежние три внешние ссылки не отправляются отдельным стартовым меню. Сайт и приглашение друга, если настроены, доступны в помощи. Во вложенных меню есть возврат. Переименование принимает следующее сообщение, удаление и отвязка требуют отдельных кнопок подтверждения. Кнопки настройки языка, разрешений, хранения файлов и выбора модели используют существующие обработчики.

Для аккаунта, которому доступен собственный нативный каталог текущего рантайма, сохраняется прежний выбор бесед. Остальные аккаунты открывают свои беседы через подписанный вход в WebApp. Общий каталог владельца им не выдаётся. Разрешения и хранение файлов другого аккаунта также открываются через его собственный WebApp; включить полный доступ общего рантайма кнопкой нельзя. Запрос на компьютер тоже проверяется: при несовпадении аккаунта задача не отправляется на устройство владельца, пользователь получает переход к своему аккаунту.

Это ограничение текущего общего рантайма. Кнопки не снимают разделение аккаунтов и не превращают его в отдельное окружение каждого посетителя.

Старые сообщения с прежними кнопками остаются в истории Telegram. Чтобы получить новую клавиатуру, достаточно один раз нажать «Начать» или отправить `/start`. Массовые сообщения пользователям и удаление их истории не выполнялись.

## Что обнаружено и исправлено

1. Стартовые ссылки, команды и вложенное меню представляли разные наборы действий. Основные действия собраны в постоянной клавиатуре, список команд сокращён.
2. Кнопка «Компьютер» создавала навигационный токен, который обработчик не принимал. Путь восстановлен.
3. Обычный пользователь публичного бота мог получить отказ в меню из-за отсутствия локального одобрения. Допуск к личному меню теперь учитывает публичный режим и проверяет совпадение физического Telegram-чата с отправителем. Групповой чат не становится личным меню.
4. Публичный локально одобренный Telegram-чат мог использовать аккаунт машины. Для публичного Telegram выбор аккаунта выполняется через облачную привязку Telegram ID. Кэш ключа и области аккаунта очищается после переподключения, успешной отвязки и выхода.
5. Старые кнопки могли применяться уже к другой выбранной беседе. Изменяющие состояние кнопки связаны с отправителем, чатом и контекстом беседы; устаревший выбор требует открыть меню заново. Удаление дополнительно связано с конкретным идентификатором беседы.
6. Нативный каталог общего рантайма не обслуживает произвольные другие аккаунты. Для них введён явный переход к собственному WebApp вместо обращения к общему каталогу. Аналогичный запрет добавлен перед выбором компьютера общего бота.
7. При первом входе в WebApp временный ключ регистрации мог остаться основным ключом входа. Теперь он отзывается, WebApp получает ключ со сроком 30 дней.
8. Ключи и cookie WebApp могли пережить отвязку Telegram от аккаунта. Добавлен учёт происхождения ключей через HMAC идентичности чата. Отзываются ключи отвязанного чата; другие отслеживаемые чаты и входы по почте сохраняются. Старые ключи без метки происхождения при отвязке отзываются консервативно, поэтому отдельным старым сессиям может потребоваться повторный вход.
9. Подтверждённый код входа на компьютер можно было подтвердить повторно от другого Telegram. Подтверждение стало однократным; проверка и использование PKCE-кода при получении ключа выполняются в одной транзакции. Групповой `/start` не подтверждает вход на компьютер.
10. WebApp мог проверить наличие данных запуска раньше загрузки Telegram SDK. Вход ожидает SDK, если данных ещё нет; при ошибке показывает восстановление. Данные из адресной строки убираются. Направление перехода ограничено своими страницами, произвольные внешние адреса не принимаются.
11. При запрете локального хранения лёгкий клиент не умеет использовать только cookie. В таком случае показывается понятная ошибка и повторная попытка, вместо перехода в интерфейс без сохранённого входа.
12. Подпись хранения файлов использовала текст подсказки с шаблоном вместо короткого названия кнопки. Добавлена отдельная подпись; предупреждение об отвязке показывается в её подтверждении.

## Проверка идентичности

- Telegram ID принимается из события Telegram или из проверенных сервером подписанных данных Mini App.
- Проверяются HMAC, срок запуска, формат пользователя и положительный числовой ID. Неподписанное число не является входом.
- Одинаковый номер в MAX и Telegram не объединяет аккаунты.
- Первый вход через Mini App и последующий вход через бота находят один аккаунт. Привязка к существующему аккаунту используется прежде создания нового.
- Локальное одобрение устройства само по себе не заменяет облачную идентичность публичного Telegram-пользователя.
- WebApp выдаёт host-only HttpOnly Secure cookie, связанную с отзывом родительского ключа.

Проверки сверены с [документацией Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) и [описанием кнопок и меню ботов](https://core.telegram.org/bots/features#keyboards).

## Серверные копии и ловушка развёртывания

Код и настройки бота: `/opt/nanolika-bot/backups/telegram-menu-20261106-d5754737`.
Код и настройки релея: `/opt/nanomuse/cloud/backups/telegram-menu-20261106-d5754737`.
Копия SQLite: `/srv/nanomuse-cloud/data/backups/telegram-menu-20261106-d5754737.db` внутри контейнера релея.

Дополнительные копии финальных ограничений и путей модулей находятся в подкаталогах первой папки.

В контейнере есть рабочая папка и установленный Python-пакет. Проверка через `python -c` из рабочей папки может показать новую копию, тогда как консольный запуск `nanomuse` использует старый пакет. В этой задаче это выявлено по неизменившемуся меню Telegram. Окончательные изменения подключены также к `/usr/local/lib/python3.12/site-packages/nanomuse/channels/`, после перезапуска проверена именно эта копия. Релейные модули проверены по фактическому пути установленного пакета, его дополнительные доработки сохранены.

При изменении содержимого уже подключённого Python-файла требуется перезапуск процесса. Один `docker compose up -d` без изменения конфигурации может не перечитать модуль. Файлы существующих одиночных подключений обновляются на месте, без подмены их inode.

Откат кода выполняется через сохранённые файлы `.before` и копии Compose с последующим запуском соответствующего сервиса. Автоматически возвращать старую базу поверх текущей нельзя: после обновления могли появиться новые пользовательские данные. Добавленная таблица происхождения ключей совместима с прежним кодом.
